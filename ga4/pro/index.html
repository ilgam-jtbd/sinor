PART 2 · 웹

웹 이벤트 — gtag 예시

중급 명세의 이벤트를 그대로 코드로 옮겨요. 이름·파라미터는 명세가 정본이에요(임의 변경 금지).

신청 완료 — consult_submit / meeting_apply
// 시럽인연 상담 신청 완료 시점
gtag('event', 'consult_submit', { source_page: 'internal' });  // 'landing' = 광고 직행

// 단체미팅 신청 완료 시점
gtag('event', 'meeting_apply', { region: 'busan', month: '2026-09' });
노출·탭 세트 — 앱 배너 예시 (IntersectionObserver로 노출 1회)
const seen = new WeakSet();
new IntersectionObserver((es) => es.forEach(e => {
  if (e.isIntersecting && !seen.has(e.target)) {
    seen.add(e.target);
    gtag('event', 'app_banner_view', { placement: e.target.dataset.place });
  }
}), { threshold: 0.5 }).observe(document.querySelector('.app-banner'));

document.querySelector('.app-banner a').addEventListener('click', () =>
  gtag('event', 'app_banner_tap', { placement: 'home' }));

제한 두 가지만 기억해요 — 이벤트 이름 40자, 이벤트당 파라미터 25개. 그리고 파라미터를 보고서에서 보려면 관리 → 맞춤 정의에 측정기준 등록(이벤트 배포와 동시에 — 소급 안 됨).

PART 3 · ⭐ 최우선

purchase 2경로 — 무통장이 빠지면 이번에도 실패예요

7개월 20건의 원인이 이거예요. 카드 결제는 브라우저에서, 무통장 입금은 입금 확인이 오프라인/어드민에서 일어나서 브라우저 이벤트로는 잡을 수 없어요. 경로를 나눠요.

경로 A — 카드 (브라우저, 결제 완료 콜백)

TossPayments 등 결제 성공 콜백에서
gtag('event', 'purchase', {
  transaction_id: 'T-20260829-0001',   // 중복 방지 키 — 주문번호 그대로
  value: 49900, currency: 'KRW',
  items: [{ item_id: 'trip_membership', item_name: '시놀트립 멤버십(1년)' }],
  method: 'card'
});

경로 B — 무통장 (서버 → GA4, Measurement Protocol)

어드민에서 입금 확인 처리하는 순간, 서버가 GA4로 직접 쏘는 방식이에요. 구글 공식 기능(Measurement Protocol)이고, api_secret은 GA4 관리 → 데이터 스트림 → 측정 프로토콜 API 비밀번호에서 발급해요.

서버 사이드 — 입금 확인 시점 (예: Node)
await fetch(`https://www.google-analytics.com/mp/collect`
  + `?measurement_id=G-DLK29GEJDF&api_secret=${SECRET}`, {   // SECRET은 환경변수로 — 코드·문서 기재 금지
  method: 'POST',
  body: JSON.stringify({
    client_id: order.gaClientId,   // 주문 생성 때 _ga 쿠키에서 저장해 둔 값
    events: [{ name: 'purchase', params: {
      transaction_id: order.id, value: order.amount, currency: 'KRW', method: 'bank'
    }}]
  })
});
주문 생성 시 client_id를 저장해 두는 게 열쇠예요. 브라우저의 _ga 쿠키 값(또는 gtag('get', …, 'client_id'))을 주문 레코드에 함께 저장해야, 나중에 서버가 쏘는 purchase가 그 사람의 여정(어디서 왔는지)과 이어져요. 이게 없으면 숫자는 잡혀도 출처 분석이 끊겨요.
PART 4 · 앱

앱 스트림 4개 — 시놀·시럽 × AOS·iOS

같은 속성(336035335)에 추가해요 — 시놀→시럽인연으로 넘어가는 여정을 한 화면에서 봐야 하니까요. 앱에 Firebase가 이미 있어 큰 개발이 아니에요(앱당 반나절 · ASO v5.1 §11).

  1. 1

    GA4에서 스트림 추가

    관리 → 데이터 수집 및 수정 → 데이터 스트림 → 스트림 추가 → Android/iOS. 기존 Firebase 프로젝트(sinor-8b864)를 이 속성에 연결해요.

  2. 2

    설정 파일 교체

    Android: 패키지명 입력(com.sinor.gathering / com.sinor_app_front) → google-services.json 교체. iOS: 번들 ID 입력 → GoogleService-Info.plist 교체. 각 앱 릴리스에 포함.

  3. 3

    앱 이벤트 부착

    중급 명세의 앱 이벤트를 Firebase Analytics로 — logEvent("tab_view", bundleOf("tab" to "home")) 식. 앱 내 결제는 purchase(Play Billing/인앱)로 동일 스키마.

  4. 4

    수신 확인

    실시간 보고서에서 스트림별 first_open이 잡히면 연결 완료. 이때부터 설치·앱 내 행동·앱 결제가 GA4에 보여요.

교차 기기 연결이 필요해지면 user_id(로그인 회원 ID의 해시)를 웹·앱 양쪽에 설정하는 걸 다음 단계로 검토해요 — 시놀↔시럽 계정 구조 확정(정본 §6 가설) 후가 좋아요.
PART 5 · 구글 생태계

시놀·시럽 구글 연결 지도 — 무엇을, 왜 연결하나

전부 무료예요. "연결하는 이유"가 시놀 실측과 어떻게 이어지는지까지 적었어요 — 이유가 약한 건 뒤로 미뤄도 돼요.

도구우선순위연결하는 이유 (시놀 관점)어떻게
GTM
(태그 관리자)		① 지금아임웹 <head>에 컨테이너 한 번만 심으면, 이후 이벤트 추가·수정을 개발 배포 없이 콘솔에서 해요. 중급 명세의 웹 이벤트 전부를 GTM으로 운영하면 아임웹 제약을 우회할 수 있어요. 네이버 전환 스크립트도 GTM 안에서 관리tagmanager.google.com → 컨테이너 생성 → head 스니펫 1회 삽입 → GA4 구성 태그 + 이벤트 태그
Search Console
(서치콘솔)		① 지금유입의 57%가 검색인데 무슨 검색어인지 모르는 상태를 끝내요. 제목 재작성(SEO 로드맵 1단계)의 전후 비교가 여기서만 가능. GA4와 연결하면 검색어→행동을 한 화면에서search.google.com/search-console 속성 등록·소유확인 → GA4 관리 → 제품 링크
Firebase① 지금앱 스트림 4개의 기반(PART 4). 이미 프로젝트(sinor-8b864)가 있어 재사용. 덤으로 FCM 푸시(무료 — 마이 뱃지·대화 알림)·Crashlytics(무료 — 앱 오류 수집)까지 같은 콘솔에서기존 프로젝트를 GA4 속성에 연결 (PART 4 절차)
Looker Studio② 곧이미 쓰고 있어요(장기 리포트가 루커스튜디오 실측). GA4·서치콘솔을 붙여 대표 보고용 한 장 대시보드로 — 화면 변경 지도(중급 ③)의 목표·가드레일을 한 화면에lookerstudio.google.com → GA4·Search Console 커넥터
비즈니스 프로필② 곧구글 지도·검색의 회사 패널. GEO(브랜드 엔티티) 전략의 무료 앵커 — 시놀(주)를 구글이 "실체 있는 회사"로 인식하게. 언론보도·sameAs와 한 세트business.google.com 등록·소유확인
Google Ads③ 나중지금 광고는 네이버 중심이라 급하지 않아요. 연결해 두면 GA4 잠재고객(중급 ⑤ — "상담 보고 신청 안 한 사람")으로 리마케팅 가능. 전제: purchase·신청 이벤트가 먼저 — 전환 없이 광고 연결은 의미 없음GA4 관리 → 제품 링크 → Google Ads (집행 시점에)
BigQuery③ 나중GA4 원본 데이터 무료 내보내기. 지금은 불필요 — 이벤트가 쌓인 뒤 "무통장 vs 카드 고객 여정 차이" 같은 정밀 분석이 필요해질 때GA4 관리 → 제품 링크 → BigQuery (무료 링크)
PageSpeed Insights② 곧가드레일 "페이지 로딩 시간"(시니어 회선에 치명적)의 측정기. 화면 변경 전후로 같은 페이지를 재요 — 연결이 아니라 주기 측정 습관pagespeed.web.dev (설치 불요)
순서가 곧 이유예요 — ①(GTM·서치콘솔·Firebase)은 측정 공백을 끝내는 도구라 지금, ②는 측정이 흐르기 시작하면, ③은 데이터가 쌓인 뒤에. 도구를 먼저 늘리는 게 아니라 "보이게 만든다 → 보여준다 → 깊게 판다" 순서예요. 네이버 서치어드바이저(구글 밖)는 서치콘솔과 같은 ①순위로 함께 진행해요 — 시놀은 네이버 유입이 구글의 2.2배니까요.
PART 6 · 검증

붙였으면 DebugView로 확인해요

어디방법
웹URL에 ?debug_mode=1을 붙여 접속(또는 gtag config에 debug_mode: true) → GA4 관리 → DebugView에서 이벤트가 초 단위로 흐르는지 확인
Androidadb shell setprop debug.firebase.analytics.app 패키지명 → DebugView
iOS실행 인자 -FIRDebugEnabled → DebugView
무통장 (MP)전송 전 /debug/mp/collect 엔드포인트로 보내면 페이로드 검증 응답을 받아요 — 실전 전 여기서 스키마 확인

검증 기준은 하나예요 — 테스트 결제(카드 1건·무통장 1건)가 둘 다 DebugView에 purchase로 뜨는 것. 그 캡처가 티켓의 완료 증빙이에요.

PART 7 · 잊기 쉬운 것

개인정보 — 수집을 켜면 고지도 갱신해요

  • 앱에서 분석 수집을 시작하면 Play 데이터 안전 섹션과 App Store 개인정보 라벨을 실제 수집 내용에 맞게 재제출 — 지금 두 앱 모두 "암호화 안 됨" 표시라(정본 §6), ASO의 데이터 안전 재제출과 한 번에 처리하는 게 좋아요
  • 개인정보처리방침에 Google 애널리틱스(Firebase 포함) 사용 명시
  • 이벤트 파라미터에 개인정보(이름·전화·이메일)를 넣지 않기 — 회원 식별이 필요하면 내부 ID의 해시만
  • Measurement Protocol의 api_secret은 환경변수로 — 코드·문서·커밋 어디에도 기재 금지
PART 8 · 완료 기준

배포 전 체크리스트

  • 이벤트 이름·파라미터가 중급 명세와 100% 일치 (임의 명명 없음)
  • 노출·탭·전환 3종이 세트로 들어감 (하나만 있는 기능 없음)
  • 맞춤 측정기준 등록을 이벤트 배포와 같은 날 완료
  • 카드·무통장 테스트 purchase가 DebugView에서 확인됨 (캡처 첨부)
  • 주문 레코드에 client_id 저장 로직 포함
  • 앱 4스트림 first_open 수신 확인
  • 서치콘솔 연결 + 네이버 전환 스크립트 설치
  • Play 데이터 안전·iOS 라벨 재제출 일정 잡힘
  • 측정 배포 후 화면 변경 착수 (순서 역전 금지 — 중급 ③ 지도)
