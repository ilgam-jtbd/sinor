# Claude Code(+Codex) 토큰·성능·충돌 문제 해결 가이드
**대상**: 시놀 시럽 프로젝트 (Codex + Claude Code 병행 작업)
**작성**: 2026-08-29 · Grabity(모닥불 공방) 클로드 코드 실전 팁 1~4편 재구성
**목적**: "토큰 사용이 너무 빠르다"는 증상을 원인별로 진단하고, 각 원인에 맞는 해결 순서를 제공

## 0. 이 문서 사용법

"토큰이 빨리 닳는다"는 하나의 증상이지만 원인은 최소 4갈래입니다. **원인을 먼저 확인하지 않고 설정을 이것저것 바꾸면, 뭘 고쳐서 나아졌는지도 같이 잊어버립니다.** 아래 순서를 지키세요.

```
진단 → 한 가지만 변경 → 같은 작업으로 재확인 → 유지 또는 되돌림
```

**5분 진단 프롬프트** (파일·설정을 바꾸지 않고 진단만 함):

```
내 Claude Code가 토큰을 너무 빨리 쓰는 원인을 먼저 점검해줘. 아직 파일과 설정은 바꾸지 마.

1. 지금 세션의 /context를 보고, 큰 항목이 무엇인지 설명해줘.
2. 현재 프로젝트에 적용되는 CLAUDE.md와 주요 지침 파일이 너무 크거나 중복되는지 확인해줘.
3. MCP는 실제 컨텍스트 비용, 연결 오류, 항상 미리 불러오는 설정이 있는지만 확인해줘.
4. 특정 동작만 느리다면 Hook이나 그 명령 자체가 원인인지 구분해줘.
5. ~/.claude/projects 에 세션 기록이 얼마나 쌓였는지도 가볍게 확인해줘.
6. 모델, 네트워크, 백그라운드 빌드처럼 클로드 밖의 원인도 짧게 점검해줘.

결과는 아래 형식으로 보여줘.
- 가장 가능성 큰 원인 1~2개
- 그렇게 판단한 근거
- 내가 다음으로 직접 확인할 명령이나 화면
- 바꾸기 전에 내 확인이 필요한 항목
```

이 진단이 한 곳을 뚜렷하게 가리키면 아래에서 해당 섹션만 읽으면 됩니다. 애매하면 1→2→3→4 순서로 하나씩 확인하세요.

## 1. 원인 진단 — 느려진/비싸진 시점부터 구분

| 증상 | 먼저 볼 곳 |
|---|---|
| 답을 시작하기 전부터 오래 걸림/토큰이 많이 나감 | 컨텍스트, 모델, 네트워크 |
| 특정 도구·명령을 쓸 때만 늦음 | MCP, Hook, 그 명령 자체의 실행 시간 |
| 테스트·빌드가 오래 걸림 | Claude/Codex가 아니라 프로젝트 명령, 디스크, 백그라운드 작업 |

**새 대화를 켠 직후에도 `/context`가 비어있지 않은 것은 정상**입니다 — 시스템 프롬프트·CLAUDE.md·auto memory가 항상 먼저 채웁니다. 문제는 "0이 아님"이 아니라 "예상보다 큰 항목이 뭔지"입니다.

### 1-1. 세션 컨텍스트가 원인일 때
`/context`(더 자세히는 `/context all`)로 항목별 크기를 확인하고, [2장](#2-컨텍스트-관리-실전)으로.

### 1-2. CLAUDE.md·지침 파일이 원인일 때
200줄을 넘거나 오래된 규칙이 섞여 있으면 [3장](#3-claudemd-체계적-관리)으로.

### 1-3. Hook이 원인일 때
플러그인·하네스를 설치할 때마다 Hook이 따라 붙습니다. 도구 하나 쓸 때마다 여러 Hook이 순서대로 돌면서 컨텍스트를 계속 주입하면, 그중엔 지금 작업과 무관한 내용도 섞입니다. `/hooks`로 목록을 봅니다.

**Hook 점검 프롬프트** (삭제·수정 전 진단만):
```
내 Claude Code에 설정된 Hook을 점검해줘. 아직 삭제하거나 수정하지 마.

Hook마다 아래를 알려줘.
- 언제 실행되는지
- 어떤 명령이나 스크립트를 돌리는지
- 매번 기다려야 하는 동기 작업인지
- 다른 Hook과 겹치거나(★충돌) 지금 쓰지 않는지
- 지웠을 때 어떤 기능이 사라지는지

느려짐/토큰 소모와 관련 있을 가능성이 큰 순서로 정리하고, 변경이 필요하면 안전한 변경안을 먼저 보여줘.
```

**충돌(conflict) 유형**: 같은 이벤트(예: PostToolUse)에 여러 Hook이 걸려 있으면 실행 순서가 꼬이거나 중복 컨텍스트 주입이 생깁니다. 위 프롬프트의 "다른 Hook과 겹치는지" 항목이 바로 이걸 잡아냅니다. `.claude/settings.json`과 `.claude/settings.local.json`에 같은 이벤트가 중복 등록돼 있는지도 함께 확인하세요.

### 1-4. 세션 기록(디스크) 문제
`~/.claude/projects`에 세션 로그가 쌓입니다. **이건 매 요청의 응답 속도/토큰량을 직접 늘리지는 않습니다** — 지금 세션이 읽는 건 그 세션 자체의 컨텍스트일 뿐, 전체 로그를 뒤지지 않기 때문입니다. 다만:
- 디스크 용량을 차지
- 프로젝트 폴더가 iCloud/Dropbox 같은 동기화 폴더 안에 있으면 동기화 자체가 버벅일 수 있음 → 시놀 시럽 저장소가 클라우드 동기화 폴더 안에 있는지 확인해볼 만합니다.

**정리 프롬프트** (백업 없이 바로 삭제 금지):
```
Claude Code 세션 기록이 얼마나 쌓였는지 보여줘.
~/.claude/projects 를 기준으로 오래됐거나 용량이 큰 것부터 순서대로 정리해주고,
지워도 괜찮은 것부터 후보로 알려줘. 아직 삭제하지 마.

지울 파일이 정해지면
1. 먼저 백업할 위치를 제안하고
2. 백업이 끝난 뒤에만 삭제해줘.
```

### 1-5. 모델·네트워크·환경
| 작업 유형 | 추천 모델 급 |
|---|---|
| 오타·포맷 정리, 짧은 질문 | 가벼운 모델 |
| 일반적인 기능 구현, 리뷰 | 중간 모델 |
| 복잡한 설계, 까다로운 버그 | 상위 모델 |

오타 수정에 최상위 모델을 쓰는 건 편의점 갈 때 택시를 부르는 것과 같습니다. 작업마다 모델을 바꾸기 번거로우면, "지금 하는 작업이 어느 쪽에 가까운지"만 가끔 점검해도 충분합니다.

컨텍스트·설정이 다 괜찮다면 도구 밖도 확인:
- **네트워크**: VPN·프록시를 거치는지, 지연이 큰 회선인지
- **디스크 I/O**: 프로젝트 폴더가 네트워크 드라이브/동기화 폴더 안에 있는지 (생각보다 큰 영향)
- **도구 실행 시간**: 테스트·빌드가 원래 오래 걸리는 것과 AI 응답 지연을 구분

### 1-6. MCP는 보통 원인이 아님
연결된 MCP 도구는 기본적으로 **이름만 먼저 로드**되고, 실제 설명(스키마)은 필요할 때 지연 로드됩니다(Dynamic Loading, `ENABLE_TOOL_SEARCH=auto`가 기본 — 컨텍스트의 10% 안에 들어갈 때만 미리 로드). **MCP가 여러 개라고 바로 느려지지 않습니다.** CLAUDE.md·Hook과 자주 같이 의심받지만 성격이 다르므로 점검 순서에서 뒤로 미뤄도 됩니다.

의심될 때만 쓰는 진단:
```
현재 연결된 MCP를 점검해줘. 아직 활성화 상태나 설정은 바꾸지 마.

서버마다 아래를 표로 정리해줘.
- 어떤 일을 하는 연결인지
- 지금 세션의 컨텍스트에 실제로 부담이 보이는지
- 연결 오류나 재연결이 반복되는지(★충돌 신호)
- 항상 미리 불러오도록 설정돼 있는지
- 처음 사용할 때만 늦는지, 매번 늦는지

마지막에는 끄거나 설정을 바꿔 볼 후보가 있다면 이유와 예상 영향을 알려줘.
확실한 근거가 없으면 "그대로 두기"라고 말해줘.
```

## 2. 컨텍스트 관리 실전

한 세션을 오래 붙잡고 있으면 성능이 나빠집니다. 방금 정한 규칙을 다시 물어보거나, 아까 읽은 파일을 또 읽는 게 신호입니다. 코드가 어려워진 게 아니라 컨텍스트가 찬 것입니다.

### 2-1. 컨텍스트가 찼을 때 — 다섯 가지 선택지

| 수단 | 고르는 상황 | 대화 기록 |
|---|---|---|
| `/clear [이름]` | 주제가 바뀌어 앞 내용이 필요 없을 때 | 비우고 새로 시작 |
| `/compact [지시]` | 같은 대화를 이어가면서 자리만 비우고 싶을 때 | 요약으로 남음 |
| handoff 문서 | 작업 내용을 파일로 넘길 때 | 문서에 적은 것만 |
| 세션 + peer messaging | 다른 세션에 이어서 시키고 싶을 때 | 보낸 텍스트만 |
| `/btw [질문]` | 곁가지 질문 하나만 하고 싶을 때 | 건드리지 않음 |

**고르는 기준은 하나**: 지금 하던 대화를 이어가야 하는지, 끊고 새로 시작해도 되는지.

#### `/clear [이름]`
```
/clear auth-refactor
```
이름을 붙이면 직전 대화에 라벨이 달려 `/resume` 목록에서 찾을 수 있습니다.

#### `/compact [지시]`
```
/compact focus on the auth bug fix
```
압축 뒤 살아남는 것:

| 항목 | 압축 뒤 |
|---|---|
| 시스템 프롬프트, 출력 스타일 | 그대로(애초에 대화 기록이 아님) |
| 프로젝트 루트 CLAUDE.md, 범위 없는 규칙 | 디스크에서 다시 주입 |
| auto memory | 디스크에서 다시 주입 |
| 읽거나 수정한 파일 | 최근 수정순 최대 5개까지 다시 읽음 |
| 호출했던 스킬 본문 | 스킬당 5,000 토큰, 전체 25,000 토큰까지(오래된 것부터 빠짐) |

대화 일부만 줄이려면 `/rewind`로 메시지를 고른 뒤 "Summarize from here"/"Summarize up to here"를 선택합니다.

#### handoff 문서 vs 세션+peer messaging
문서를 쓰는 동안 이미 부족한 컨텍스트를 더 쓰고, 새 세션은 그 문서를 다시 읽느라 또 씁니다. 적다가 빠뜨린 판단은 새 세션이 물어볼 데가 없습니다. **가능하면 세션을 하나 더 열고 peer messaging으로 넘기는 편이 낫습니다** — 받는 쪽이 바로 되물을 수 있고, 무엇을 적을지 미리 고르지 않아도 됩니다.

```
/list-agents
```
연결 가능한 subagent·팀원·다른 Claude Code 세션이 이름과 함께 나옵니다(cross-session messaging이 켜진 세션에서만 보임). 넘어가는 건 **평문 텍스트뿐**입니다 — 대화 기록·파일 전체는 따라가지 않으므로, "지금까지 한 일"보다 "다음에 할 일과 그 이유"를 보내는 편이 낫습니다.

#### `/btw [질문]`
메인 컨텍스트에 영향을 주지 않고 곁가지 질문만 합니다. 대화를 갈라서 실제 작업을 다른 방향으로 해보려면 `/branch`(갈라진 쪽으로 이동, 원본은 `/resume`으로 복귀)를 씁니다.

### 2-2. 덜 차게 만들기 (예방)

#### `/autocompact` — 자동 압축 시점 조정
```
/autocompact 500k
```
절대 토큰 수(100K~1M)로 지정합니다. `200`처럼 천 단위 숫자만 넣어도 됩니다(200 → 200,000). `auto`로 되돌리면 모델 기본값. **권장**: 500K 부근 — 그 이상으로 두면 오히려 성능이 나빠지는 경향이 보고됩니다.

#### 큰 읽기는 Subagent로 위임
컨텍스트를 가장 빨리 채우는 건 대화가 아니라 **읽어 들인 내용**입니다. 조사처럼 중간 과정이 긴 작업은 subagent에 보내면 파일 내용은 그쪽 컨텍스트에 쌓이고 메인 쪽에는 결론만 돌아옵니다.
```
이 저장소에서 인증 흐름이 어디서 시작하는지 subagent에게 조사시켜줘.
메인 세션에는 파일 경로와 결론만 가져와.
```
자주 쓰는 위임 에이전트는 `.claude/agents/<name>.md`에 정의해두면 매번 설명하지 않아도 됩니다. (자세한 내용은 [4장](#4-멀티-에이전트로-컨텍스트-분리))

#### 메모리 파일 정리
`/memory`로 CLAUDE.md와 auto memory를 열어 정리합니다(CLAUDE.md는 [3장](#3-claudemd-체계적-관리) 참조).

## 3. CLAUDE.md 체계적 관리

CLAUDE.md는 매 세션 시작 시 무조건 함께 읽히는 유일한 파일입니다. 문제는 "안 쓰는 것"이 아니라 **"쓰고 나서 방치하는 것"** — 좋다고 하니 계속 추가만 하고, 예전 규칙이 지금도 맞는지는 아무도 확인하지 않습니다. 방치된 CLAUDE.md는 안 쓰는 것보다 못할 수 있습니다.

### 3-1. 200줄 이하로 유지

200줄이 넘으면 일단 의심합니다. 파일시스템만 봐도 뻔한 정보(디렉터리 구조, 의존성 목록)는 빼고, **저장소의 숨겨진 함정과 관례만** 남깁니다. Codex/Claude가 코드에서 스스로 파악할 수 있는 내용까지 매 세션 다시 읽게 만들 필요는 없습니다.

`/doctor` 커맨드(Claude Code)로 자동 점검할 수 있습니다 — 코드베이스에서 알아낼 수 있는 내용은 잘라내고, 다른 방식과 다르게 동작하는 부분·함정·근거처럼 정말 남겨야 할 것만 골라 정리안을 제안합니다.

**Codex를 병행한다면**: Codex는 `AGENTS.md`를 같은 역할로 읽습니다. 두 파일에 같은 규칙을 따로 적어두면 그 자체가 중복·드리프트 원인이 됩니다 — 한쪽을 SSOT로 잡고 다른 쪽은 포인터만 남기는 걸 권장합니다.

### 3-2. 조건부 로딩으로 분할

CLAUDE.md 하나에 다 넣지 말고 두 가지로 나눕니다:

```
your-project/
├── CLAUDE.md               # 모든 작업에 공통되는 규칙만
├── src/
│   └── auth/
│       └── CLAUDE.md       # auth 폴더 작업할 때만 로드
└── .claude/
    └── rules/
        ├── testing.md       # 항상 로드 (paths 없음)
        └── api-style.md     # src/api/**/*.ts 건드릴 때만 로드
```

`.claude/rules/api-style.md`의 frontmatter 예:
```
---
paths:
  - "src/api/**/*.ts"
---

# API 작성 규칙
- 모든 엔드포인트에 입력 검증 포함
- 에러 응답은 표준 포맷 사용
```

- **`.claude/rules/`**: 주제별로 파일을 쪼갬(testing.md, security.md). `paths:` frontmatter가 있으면 해당 패턴 파일을 건드릴 때만 로드 — 평소엔 컨텍스트에 안 실림.
- **하위 폴더 CLAUDE.md**: 특정 폴더에 따로 둠. 그 폴더 안 파일을 열 때만 로드.

핵심은 하나: **"모든 작업에 항상 필요한 것"과 "특정 상황에서만 필요한 것"을 구분**하는 것. 루트 CLAUDE.md가 계속 늘어나면, 지우기 전에 이 둘 중 어디로 옮길 후보인지부터 봅니다.

> **주의**: `@`로 파일을 import하는 방식은 텍스트를 그대로 붙여넣기 때문에 추천하지 않습니다 — 조건부 로딩의 이점이 사라집니다.

### 3-3. 반복 실패만 기록

CLAUDE.md는 한 번에 완성하는 문서가 아니라, **같은 실수를 반복할 때만 한 줄씩 추가하는 목록**입니다. 같은 실수를 두 번 하거나, 코드 리뷰에서 몰랐어야 할 게 아닌 걸 지적받거나, 지난 세션에 했던 말을 또 하고 있다면 — 그게 빠진 한 줄입니다.

"이거 추가해줘"라고 맡기면 한 줄이 수십 줄로 부풀려지는 경우가 흔합니다. **문장 자체는 맡기되 "최대한 간결하게"를 못 박고, 어떻게 추가됐는지 항상 직접 확인**하세요.

```
지금 세션에서 반복해서 틀렸거나, 코드만으로 명시가 안되는 실수들을 짧게 정리해줘.
그리고 이걸 CLAUDE.md에 몇 줄로 추가할지 초안만 보여줘 (최대 2~3줄). 아직 파일은 건드리지 마.
```

### 3-4. 그래도 많아지면 스킬/문서로 완전히 빼기 (Progressive Disclosure)

특정 작업을 할 때만 필요한 절차, 한 번씩만 참고하면 되는 긴 설명은 CLAUDE.md에 남기지 말고 스킬이나 별도 문서로 완전히 옮기고, CLAUDE.md에는 **"이 작업을 할 땐 이 문서를 먼저 읽어라"는 포인터 한 줄만** 남깁니다.

```
배포 전 체크리스트: docs/deploy.md 참고 (배포 작업 시작할 때만 읽는다)
```

세 문장 넘게 이어지는 절차 설명이 있으면 그 부분만 별도 파일로 옮기고, 자리엔 포인터 한 줄만 남기세요.

### 3-5. Routine/cron으로 주기 점검

한 번 정리해도 시간이 지나면 다시 방치됩니다.

- **클라우드 Routine(`/schedule`)**: 매번 레포를 새로 클론해서 도는 구조라 로컬 세션 로그는 못 읽음 → git 히스토리·PR 기록만 보고 CLAUDE.md 개선안을 제안하는 용도로 사용.
- **로컬 cron**: 로컬 세션에서 있었던 일까지 반영하고 싶으면 직접 돌림.

> **어느 쪽이든 결과는 PR로만 받고, 병합은 사람이 합니다.** Claude가 CLAUDE.md를 스스로 고치게 두는 것 자체는 괜찮지만, 사람 검토 없이 바로 파일을 고치게 하면 오히려 성능이 나빠진 사례가 있습니다.

### 3-6. 체크리스트

- [ ] CLAUDE.md(및 AGENTS.md)가 200줄을 넘지 않는지 확인
- [ ] 특정 파일/폴더에만 필요한 규칙은 `.claude/rules/`나 하위 폴더 CLAUDE.md로 이동
- [ ] 규칙은 실수가 생겼을 때만 추가, 수정 시 항상 직접 확인
- [ ] 많아진 내용은 스킬/문서로 옮기고 CLAUDE.md는 포인터 역할만
- [ ] Routine 또는 cron으로 점검 주기를 걸어뒀고, 자동 병합이 아니라 PR로 받는지

## 4. 멀티 에이전트로 컨텍스트 분리

> **Codex 참고**: 아래 Subagent·Agent Teams·Cross-session messaging은 **Claude Code 전용 기능**입니다. Codex에서는 이름은 다르지만 유사한 개념(별도 스레드/세션 분리, 하위 작업 위임)이 있을 수 있으니 Codex 쪽 문서를 별도 확인하세요. 다만 **"무엇을 분리할지 먼저 정하고 결과만 가져온다"는 원칙 자체는 도구에 상관없이 적용됩니다.**

### 4-0. 세 가지 방식 구분

| 이럴 때 | 고를 방식 |
|---|---|
| 중간 과정은 필요 없고 결과만 받으면 됨 | Subagent |
| 작업자끼리 발견한 내용을 공유하고 논의해야 함 | Agent Teams |
| 내가 직접 연 Claude Code 세션끼리 연결하고 싶음 | Cross-session messaging |

이름보다 중요한 건 **왜 컨텍스트를 분리하는지**입니다.

### 4-1. Subagent
하나의 세션 안에서 별도 컨텍스트로 작업 후 결과만 메인에 돌려줍니다. 코드베이스 탐색·로그 분석·자료 조사처럼 중간 과정을 메인에 남길 필요가 없는 일에 적합.

```
이 작업은 subagent에게 맡겨줘.
메인 세션에는 결론, 근거, 다음 행동만 요약해서 가져와.
```

### 4-2. Agent Teams (실험 기능, 기본 꺼짐)
하나의 세션이 팀 리드를 맡고 나머지 팀원은 각자 독립 컨텍스트에서 작업, 공용 작업 목록과 메시지로 발견 내용을 공유. 서로 다른 가설로 버그를 조사하거나 프론트/백엔드처럼 경계는 나뉘되 조율이 필요한 일에 적합. 결과 하나만 받으면 되면 Subagent가 더 가볍습니다.

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

**주의**: 팀원마다 별도 인스턴스를 쓰므로 토큰 사용량과 조율 비용이 큽니다. 순차 작업이나 같은 파일을 함께 고치는 일에는 단일 세션/Subagent가 더 잘 맞습니다. **시놀 시럽처럼 토큰 절약이 우선순위라면 Agent Teams는 신중하게 — 오히려 토큰을 더 씁니다.**

### 4-3. Cross-session messaging
이미 실행 중인 독립 세션을 그대로 연결(팀원을 새로 만드는 게 아님). 한 세션의 결정을 다른 세션에 넘기거나, 별도 worktree에서 병렬 작업 중인 세션끼리 변경 사항을 알릴 때 유용.

- macOS/Linux/WSL2: Claude Code v2.1.224 이상
- 네이티브 Windows: v2.1.234 이상
- 넘어가는 건 텍스트뿐(대화 기록·파일 전체는 안 넘어감) — 같은 대화를 다른 터미널에서 이어가려면 메시지 대신 해당 세션을 재개(resume).

```
/list-agents   # 연결 가능한 세션 확인
```

### 4-4. 항상 빠른 건 아님
작업이 짧거나 순서대로 진행해야 하면 메인 세션 하나로 끝내는 게 빠릅니다. 에이전트를 나누면 지시·결과 취합 비용이 생깁니다. **여러 작업이 정말 독립적인지, 분리 이점이 조율 비용보다 큰지** 먼저 보세요.

### 4-5. Codex + Claude Code 동시 작업 시 "충돌" 주의사항

두 도구를 같은 저장소에서 병행할 때 실제로 자주 생기는 충돌:

1. **같은 파일 동시 수정**: 한쪽이 편집 중인 파일을 다른 쪽이 동시에 열어 덮어쓰는 경우 → git worktree로 물리적으로 작업 공간을 분리(`git worktree add`)하거나, 한 파일/모듈은 한 도구만 담당하도록 역할을 미리 나누세요.
2. **CLAUDE.md vs AGENTS.md 규칙 불일치**: 3-1 참고 — 한쪽을 SSOT로 정하고 다른 쪽은 포인터.
3. **Git 상태 충돌**: 한쪽이 커밋하는 중에 다른 쪽이 같은 브랜치에 push하면 충돌. 도구별로 브랜치를 분리하고 PR로 합류시키는 편이 안전합니다(이 저장소 VELOR에서도 실제로 쓰는 패턴).
4. **Hook 중복 실행**: 두 도구가 각자 자기 Hook 체계를 갖고 있으면, 같은 트리거(예: pre-commit)에 두 도구의 훅이 겹쳐 걸릴 수 있습니다 — 1-3 진단 프롬프트로 확인.

## 5. 토큰을 미리 줄이는 오픈소스 도구

컨텍스트·CLAUDE.md·Hook까지 다 정리했는데도 도구 결과나 로그가 유난히 크다면, 전달되기 전에 내용 자체를 줄여주는 도구를 고려합니다. 세 개가 줄이는 지점이 각각 달라 같이 써도 겹치지 않습니다.

| 도구 | 어디서 줄이나 | 주장 수치 | 링크 |
|---|---|---|---|
| RTK | 명령 실행 결과가 컨텍스트에 닿기 전 | 토큰 80% 감소 | https://github.com/rtk-ai/rtk |
| Headroom | 파일과 데이터를 읽어 들이는 단계 | 토큰 87.6% 감소 | https://github.com/chopratejas/headroom |
| Caveman | 모델이 답을 내보내는 단계 | 출력 토큰 65% 감소 | https://github.com/JuliusBrussee/caveman |

> 수치는 각 저장소 자체 공개 값이며, 작업 성격에 따라 크게 달라질 수 있습니다. 붙이기 전/후로 같은 작업을 돌려 비교하세요.

### 5-1. RTK — 명령 출력 필터링
```
brew install rtk && rtk init -g
rtk gain   # 얼마나 줄었는지 확인
```
빌드 로그·테스트 출력처럼 길고 다시 볼 일 없는 내용이 컨텍스트를 가장 크게 먹습니다. RTK는 모델에 닿기 전에 중복 로그를 접고, 파일을 디렉터리별로 묶고, 군더더기를 지웁니다. **Bash 도구 호출에만 걸립니다** — Claude Code 내장 도구는 Hook을 거치지 않아 그쪽 내용은 그대로 쌓입니다.

### 5-2. Headroom — 읽어 들이는 데이터 압축
```
pip install headroom-ai[all]
headroom wrap claude
```
파일·JSON·대화 기록을 종류에 맞게 압축, 모델이 원본을 필요로 하면 다시 꺼내줍니다. 큰 파일을 자주 읽는 작업에 적합. `http://localhost:7878/dashboard`에서 실시간 절감량 확인 가능. `wrap`(기존 사용법 그대로) 외 `proxy`, MCP 서버(`headroom_compress`, `headroom_retrieve`) 방식도 있습니다.

### 5-3. Caveman — 출력 압축
```
claude plugin marketplace add JuliusBrussee/caveman
```
인사말·군더더기를 걷어내고 핵심만 남기되 코드·URL은 그대로 둡니다. 압축 강도는 `lite`(문법 유지)/`full`(기본)/`ultra`(최대) 중 선택. 대화가 길어질수록 모델 자신의 답변도 컨텍스트에 쌓이므로, 특히 긴 세션에서 효과가 큽니다.

**셋을 한꺼번에 붙이기보다** `/context`에서 무엇이 자리를 많이 먹는지 먼저 보고 고르세요 — 명령 출력이 문제면 RTK, 큰 파일이 문제면 Headroom, 대화가 길어서면 Caveman.
