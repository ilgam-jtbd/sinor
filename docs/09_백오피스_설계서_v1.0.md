## 0. 왜 필요한가 · 기존 관리자 현황

**핵심 원칙** — 개발 배포 없이 바꿀 수 있는 범위가 곧 그로스 실험의 속도입니다. 운영 변경마다 개발 배포가 필요하면 개선 주기가 스프린트 단위로 늘어나 실험이 사실상 불가능해집니다.

**기존 관리자 화면 추적 결과 — 2026-08-09 정정** 【확정】

> **정정 이력** — 초판에서 "관리자 화면 부재 → 신설"이라고 썼으나 **틀렸습니다.** APK 바이너리만 보고 내린 결론이었고, 어드민은 **별도 웹**이라 APK에 없는 것이 당연했습니다. 슬랙 `30_시놀_기획-개발` 채널 확인 결과 어드민은 **이미 존재하며 활발히 개발 중**입니다.

- **기존 어드민 2종 존재 확인** 【확정 — 슬랙 티켓】 — **시놀 어드민** · **시럽인연 어드민**. 확인된 기능: 대시보드(월별 매출 추이 `SN-2199` · 월별 매칭 현황 `SN-2196` · 매칭매니저별 현황 `SN-2197` · 성별·연령대·지역 통계 `SN-2195`) · 관리자 설정 — 매니저 관리(`SN-2198`) · 준회원 관리(`SN-2205`·`SN-2207`) · 프로필·서류 첨부(`SN-2200`).
- APK 역컴파일에서 앱 내 관리자 화면이 없었던 것은 **사실이며 유효**합니다. 검출된 admin 문자열은 전부 SDK 소속입니다(Easemob 그룹 방장, Firebase/AppLovin MAX, MySQL 드라이버). 다만 이 사실에서 "회사에 어드민이 없다"를 끌어낸 것이 오류였습니다.
- 웹(아임웹)은 **페이지 편집형 CMS만** 있어 홈 섹션 순서·수익 카드 노출·이벤트 예산 같은 **동적 제어는 여전히 불가**합니다. **아임웹 종료가 임박했다는 보고가 있어**(슬랙 7/1 기준 「약 40일」 → 2026-08-10 추정) 아임웹 확장 선택지는 사라질 수 있습니다 — **종료일 확인이 선행 과제**입니다 【유력】.
- **결론(수정)** — 이 문서는 신설 설계가 아니라 **「기존 어드민 2종 + 운영 레이어 확장」**입니다. 콘텐츠·이벤트·수익 카드·홈 섹션 제어처럼 **지금 어디에도 없는 것**이 신규 범위이고, 대시보드·회원·매칭 관리처럼 **이미 있는 것**은 중복 개발 대상이 아닙니다.

> **선행 과제 — 기존 어드민 실제 화면 목록 확보.** 목록이 없으면 이 문서의 12메뉴 중 무엇이 신규인지 셀 수 없습니다. 화면 캡처 또는 메뉴 트리를 받아 대조한 뒤 신규 범위를 확정합니다.

## 1. 설계 원칙

1. **운영자가 배포 없이 바꾸는 범위 = 이 도구의 완료 조건.** §4의 8종은 전부 어드민에서 수정 가능해야 합니다.
2. **미리보기 필수.** 저장 전 실제 화면과 동일한 미리보기를 제공합니다. 시니어 화면에서 잘린 문구·빈 이미지는 오류로 읽힙니다.
3. **가격은 상품 DB 연동.** 하드코딩 금지 — 불일치 민원의 직접 원인입니다.
4. **측정은 콘텐츠와 한 몸.** 항목을 만들면 노출·탭·전환 이벤트가 자동 부착됩니다. "나중에 붙임" 금지.
5. **권한 분리.** 콘텐츠 운영·이벤트(예산)·상품(가격)·측정은 역할이 다릅니다.
6. **수치는 정합기준 정본(`docs/03`) 단일 출처.** 백오피스 입력값도 정본과 어긋나면 경고합니다.

## 2. IA — 메뉴 구조

```
① 대시보드      오늘의 매출·설치·이벤트 성과 요약 + 처리 대기
② 콘텐츠 관리    홈 섹션 순서 · 기획전 배너 · 수익 카드 3종 · 카테고리 · 칼럼 하단 카드 · 빈 상태 문구
③ 이벤트 관리    친구초대 5,000원 · 모임개설 11만P — 예산·기간·어뷰징·성과
④ 상품·구매 관리  단체미팅 일정 · 시럽인연 상담/패키지 · 시놀트립 멤버십   ※ 기존 확정분 승계
⑤ 커뮤니티·매칭   모임 · 스토리(후기/칼럼) · 대화 운영공지·자동초대        ※ 기존 확정분 승계
⑥ 회원 관리      인증 심사 · 신고 처리 · 상태(휴면·탈퇴) — 개인정보 최소 접근
⑦ 알림 관리      푸시·인앱·알림톡 · 세그먼트 · 발송 규칙
⑧ 자동화         에이전트 작업 목록 · 실행 로그 · 승인 대기
⑨ QA·개선 요청   [탭1] QA(버그)  [탭2] 개선 요청 — 에이전트 1차 응답 · MCP 이슈·릴리즈 연동
⑩ 그로스·실험    A/B 테스트 · CRO 퍼널 · 실험 등록·판정·롤백
⑪ 측정 연결      이벤트 부착 현황 · 전환추적 · 검색어 로그
⑫ 설정           회원 권한(RBAC) · 노출 규칙 · 웹뷰 맥락 · 앱 유도 규칙
```

**④·⑤는 신규 설계가 아니라 기존 확정분을 그대로 가져옵니다.** 상품 구매 관리(단체미팅 일정·시럽인연 패키지·시놀트립 멤버십)와 매칭·대화 운영은 이미 개발 요구서 §4와 기획 확정본에서 합의된 내용이며, 백오피스는 그 값을 **입력·조회하는 자리**일 뿐입니다. 이 문서에서 상품 구조나 매칭 규칙을 다시 설계하지 않습니다.

개인정보(회원 상세)는 이 도구에서 **조회·다운로드하지 않습니다.** 통계·집계만 봅니다.

### 3-2-1. QR 자동 적립의 어뷰징 위험 — 구체적입니다

QR 스캔 → **제휴처 계정에 5,000P 자동 적립 → 현금 출금 신청 가능**은 **스캔만으로 현금이 나가는 구조**입니다.

| 시나리오 | 결과 |
|---|---|
| 번호를 바꿔가며 반복 가입 | 스캔 수만큼 현금 |
| 대포번호·가상번호 대량 가입 | 대량 인출 |
| 가입 직후 이탈(실사용 0) | CAC만 나가고 MAU 기여 없음 |

**최소 방어선 4가지(권고)** — ① 계정·기기·일자당 지급 상한 ② 지급 즉시 출금이 아니라 **유예**(가입자 최소 활동 확인 후 확정) ③ 동일 기기·IP 반복 **탐지(L3)** ④ **현금 출금은 사람 승인**(3-7 「예산 집행은 자동화하지 않음」과 동일선).

> **예산 한도·어뷰징 정책은 경영 결정 대상**입니다(현재 대기). 백오피스는 그 값을 **입력·집행·모니터링**하는 자리이며, 정책 자체를 문서에 임의로 확정하지 않습니다.

## 3-5. 회원 관리 — 개인정보 최소 접근 원칙

운영에 반드시 필요한 기능이지만, **회원 상세 정보를 마음대로 보는 도구가 되면 안 됩니다.** 아래 원칙을 시스템으로 강제합니다.

| 원칙 | 구현 |
|---|---|
| 기본은 마스킹 | 이름·연락처·생년월일은 기본 마스킹(홍○○ · 010-****-1234). 해제하려면 **사유 입력 + 로그 기록** |
| 목록은 집계만 | 회원 목록은 상태·등급·활동 지표만. 개인 식별 정보 열 없음 |
| 다운로드 금지 | CSV·엑셀 내보내기 기능을 만들지 않습니다 |
| 접근 로그 | 누가·언제·어떤 회원을·왜 열었는지 전부 기록. 관리자만 열람 |
| 보존 기간 | 탈퇴 후 법정 보존 기간 경과 시 자동 파기 큐 |

**운영자가 실제로 하는 일**

| 업무 | 화면 | 자동화 |
|---|---|---|
| 본인인증 심사 | 대기 큐 → 승인/반려 | **L2** — AI 1차 판정 후 사람 승인 |
| 신고 처리 | 신고 큐 → 경고·정지·해제 | **L2** — 유형 분류·증거 요약 자동, 제재는 사람 |
| 이상 행동 탐지 | 위험 신호 대시보드 | **L3** — 탐지·알림만 |
| 휴면·탈퇴 | 상태 전환·복구 | **L1** — 정책 기준 자동 전환 |
| 등급·권한 | 매니저 배정·VIP 표시 | 수동 |

> **로맨스스캠·피싱은 시니어 서비스의 최대 리스크**입니다. 앱이 이미 「5중 AI 여성안심」을 표방하므로, 백오피스는 그 탐지 결과를 **처리하는 창구**여야 합니다.

## 3-6. 알림 관리 — 리텐션의 실행 도구

| 채널 | 용도 | 비고 |
|---|---|---|
| 푸시(FCM) | 모임·대화·미팅 공지 | 앱이 이미 Firebase Messaging 사용 |
| 인앱 배너 | 이벤트·기획전 | 홈 섹션과 노출 규칙 공유 |
| 카카오 알림톡 | 결제·신청 확인, 집결 안내 | 미설치 시 확인 필요 |

**발송 규칙 (가드레일)**

1. **빈도 상한** — 1인 1일 N건. 초과분은 자동 보류
2. **수신 시간대** — 야간(21시~익일 9시) 발송 차단, 예약으로 전환
3. **수신거부 존중** — 마케팅성은 동의자에게만. 거래성(결제·집결)은 별도
4. **세그먼트** — 지역·관심사·참여 이력·휴면 여부. **개인 식별 없이 조건으로만**
5. **A/B** — 문구 2안 발송 후 오픈률 비교. 불가하면 대체 판정 방법을 함께 기록

**핵심 발송 시나리오**

| 시나리오 | 트리거 | 자동화 |
|---|---|---|
| 단체미팅 잔여 3석 | 잔여석 임계 도달 | **L1** — 관심 회원에게 자동 발송 |
| 무통장 입금 미완료 | 신청 후 D+1 / D+3 | **L1** — 결제 완료율 직결 |
| 여행·미팅 집결 안내 | 출발 D-1 | **L1** — 해당 일정 대화방 자동 공지 |
| 모임 방치 | 최근 활동 30일 없음 | **L2** — 방장에게 초안 제안 |
| 후기 요청 | 일정 종료 D+1 | **L1** — 스토리 콘텐츠 확보 |
| 휴면 예정 | 미접속 60일 | **L2** — 부활 캠페인 초안 |

## 3-7. 에이전트 자동화 — 무엇을 맡기고 무엇을 사람이 하는가

**자동화 레벨**

| 레벨 | 정의 | 적용 기준 |
|---|---|---|
| **L1 자동 실행** | 에이전트가 바로 수행 | 되돌릴 수 있고 · 규칙이 명확하고 · 개인에게 불이익 없음 |
| **L2 초안 → 승인** | 에이전트가 만들고 사람이 발행 | 문구·제재·예산이 걸린 일 |
| **L3 탐지 → 알림** | 에이전트는 알리기만 | 판단이 어렵거나 위험이 큰 일 |

**절대 자동화하지 않는 것** — 제재(정지·탈퇴), 환불·결제 취소, 개인정보 열람, 예산 집행, 가격 변경. 전부 사람 승인이 필요합니다.

**자동화 대상**

| # | 업무 | 레벨 | 효과 |
|---|---|---|---|
| 1 | 단체미팅 잔여석 임박 알림 | L1 | 매출 — 마감 임박 전환 |
| 2 | 무통장 미입금 리마인드 | L1 | 매출 — 결제 완료율(현재 최대 누수) |
| 3 | 집결·출발 공지 발송 | L1 | CS 감소·노쇼 방지 |
| 4 | 후기 요청 → 스토리 큐 적재 | L1 | 콘텐츠 확보·사회적 증거 |
| 5 | 칼럼 191편 주제 분류 → 하단 카드 6종 매핑 | **L2** | 전환 — 재혼→시럽인연, 건강→모임, 여행→트립 |
| 6 | 검색어 0건 로그 → 콘텐츠 갭 리포트 | L1 | 공짜 키워드 리서치(5,683회 실측) |
| 7 | 본인인증 서류 1차 판정 | **L2** | 심사 시간 단축 (앱에 ML Kit Face 이미 탑재) |
| 8 | 신고 유형 분류·증거 요약 | **L2** | 처리 속도 — **제재는 사람** |
| 9 | 로맨스스캠·피싱 패턴 탐지 | **L3** | 신뢰 — 시니어 최대 리스크 |
| 10 | 이벤트 어뷰징 탐지(중복 계정·자기 초대) | **L3** | 예산 보호 |
| 11 | 모임 방치 감지 → 방장 알림 초안 | L2 | 리텐션 |
| 12 | 가드레일 위반 감지(수익카드 연속배치 등) | L1 | 품질 — 저장 단계 차단 |
| 13 | 주간 운영 리포트 자동 생성 | L1 | 판정 근거 축적 |
| 14 | 휴면 예정 부활 캠페인 초안 | L2 | MAU |

**자동화 실행 로그** — 모든 L1 실행은 사후 검토가 가능해야 합니다. 무엇을·언제·몇 건·왜 실행했는지 기록하고, 운영자가 **되돌리기(rollback)** 할 수 있어야 합니다.

**측정 선행 원칙은 여기서도 같습니다.** 자동화가 성과를 냈는지 판정하려면 이벤트가 먼저 붙어 있어야 합니다.

## 3-8. QA · 개선 요청 — 운영자↔개발자 창구를 하나로

운영자가 문제를 발견해도 지금은 **말할 곳이 정해져 있지 않습니다.** 카톡·구두·회의로 흩어지면 재현 정보가 사라지고, 개발자는 "무슨 화면에서 무엇을 눌렀는지" 되묻는 데 시간을 씁니다. 그래서 **한 메뉴 · 두 탭**으로 묶습니다.

| 탭 | 다루는 것 | 예 |
|---|---|---|
| **[탭1] QA (버그)** | 지금 동작이 잘못된 것 | 가격이 화면마다 다름 · 대화방 안 읽음 점이 안 사라짐 · 결제 후 초대 누락 |
| **[탭2] 개선 요청** | 지금 동작은 맞지만 바꾸고 싶은 것 | 홈 첫 화면에 이벤트를 하나 더 · 배너 문구를 요일별로 · 후기 상단 고정 |

**접수 시 자동 수집** — 운영자는 화면에서 「신고」만 누릅니다. 화면 경로·앱 버전·기기·OS·재현 단계·최근 콘솔 오류·스크린샷을 시스템이 붙입니다. 운영자에게 재현 절차를 글로 쓰게 하지 않습니다(대부분 못 씁니다).

### 3-8-1. 에이전트가 먼저 답합니다 — 개발자는 마지막에 부릅니다

접수 즉시 에이전트가 1차 응답합니다. 개발 이관은 **에이전트가 해결하지 못한 것만** 갑니다.

| 분류 | 판정 | 레벨 | 에이전트 행동 |
|---|---|---|---|
| **A. 이미 되는 것** | 기능은 있는데 위치를 모름 | **L1** | 즉시 답변 + 해당 화면 딥링크 + 3줄 사용법. 종결 |
| **B. 설정으로 되는 것** | 백오피스 값 변경으로 해결 | **L2** | 바꿀 값의 **초안(변경 전/후)** 을 만들어 승인 요청. 승인 시 적용·로그 |
| **C. 문서에 답이 있는 것** | 규격상 의도된 동작 | **L1** | 근거 문서 구절 인용 + 왜 그렇게 정했는지. 이견이면 [탭2]로 전환 |
| **D. 개발이 필요한 것** | 코드 변경 필요 | **L2** | 재현 확인 → **이슈 초안**(재현·기대·실제·영향 범위·관련 파일 추정) 작성 → 승인 후 이슈 생성 |
| **E. 판단이 필요한 것** | 정책·가격·개인정보·제재 관련 | **L3** | 답하지 않고 담당자에게 넘김 |

> **에이전트가 답하지 않는 것** — 환불 여부, 제재 여부, 가격 변경, 개인정보 관련 문의. 3-7의 「절대 자동화하지 않는 것」과 같은 선입니다.

### 3-8-2. MCP 연동 — 이슈부터 릴리즈까지 한 줄로

에이전트가 백오피스 안에서 **개발 도구를 직접 조작**합니다. 아래는 지금 세션에 **실제 연결되어 있는 MCP 서버**입니다 【확정 — 연결 목록 확인】. 새로 사야 하는 도구가 아닙니다.

| MCP | 에이전트가 하는 일 | 레벨 |
|---|---|---|
| **GitHub** | 이슈 생성·라벨·중복 검색 · PR 링크 연결 · **릴리즈 노트 초안 작성 · 릴리즈 발행** | 이슈=L2 · **릴리즈 발행=L2(사람 승인 필수)** |
| **Linear** | 티켓 생성·상태 동기화·사이클 배치 | L2 |
| — | **GitHub + Linear 병행 확정**(2026-08-09). 역할 분담 — GitHub = 기록 원본(이슈·PR·릴리즈), Linear = 일정·담당·사이클. **상태의 원본은 GitHub 이슈**로 고정하고 에이전트가 Linear로 단방향 반영합니다. 두 곳이 서로 다른 상태를 갖는 것을 막기 위함입니다 | — |
| **Sentry** | 접수된 버그를 실제 오류 이벤트와 자동 연결 · 발생 건수·영향 사용자 수 첨부 | **L1** (읽기만) |
| **Slack** | 담당자 호출·처리 결과 통지 | L1 |

**릴리즈 흐름** — `접수 → 에이전트 1차 응답 → (D분류) 이슈 초안 → 승인 → GitHub 이슈 → 개발·PR → 머지 → 에이전트가 릴리즈 노트 초안(운영자가 읽을 한국어로) → 승인 → 릴리즈 발행 → 접수 건 자동 종결 알림 → 운영자 확인`

> **릴리즈 발행을 L1로 두지 않습니다.** 되돌리기 비용이 큰 대외 행위이기 때문입니다. 에이전트는 **노트를 쓰고 버튼 앞까지** 갑니다.

### 3-8-3. 측정 — 이 메뉴가 잘 굴러가는지 판정하는 값

| 지표 | 정의 | 성격 |
|---|---|---|
| **에이전트 1차 해결률** | 개발 이관 없이 종결된 비율 (A+B+C) | 성공지표 |
| 1차 응답 시간 | 접수 → 에이전트 첫 답변 | 성공지표 |
| 개발 이관 건수 | D분류 건수 | 성공지표 |
| **재오픈율** | 종결 후 같은 문제 재접수 비율 | **가드레일** — 성급한 종결 감지 |
| **오답률** | 에이전트 답변을 운영자가 「해결 안 됨」으로 되돌린 비율 | **가드레일** |
| **백오피스 접수 비율** | 전체 요청 중 이 메뉴로 들어온 비율 (나머지는 카톡·구두) | **창구 통합 판정** |

가드레일이 없으면 "빨리 닫기만 하는" 에이전트가 성공으로 읽힙니다. 창구 통합은 **접수 비율이 오르지 않으면 실패**입니다 — 통합했다고 선언하는 것과 실제로 여기로 오는 것은 다릅니다.

## 3-9. 그로스 · A/B 테스트 · CRO 자동화 — 있는 도구로, 싸게

### 3-9-1. 도구 스택 — 새로 사지 않는 것이 원칙

| 목적 | 도구 | 비용 | 근거 · 신뢰도 |
|---|---|---|---|
| 실험 배분·플래그 | **Firebase Remote Config + A/B Testing** | **무료** | **앱에 이미 탑재 확정** — APK 역컴파일에서 Remote Config 확인. SDK 추가 없음 【확정】 |

**쓰지 않는 것** — Google Optimize(2023년 종료), 유료 CRO SaaS(Optimizely·VWO 등 월 수백만원대). 지금 트래픽 규모에서 비용 대비 얻는 것이 없습니다.

**예산 원칙 (2026-08-09 확정)** — 초과분 예산 집행은 승인됐습니다. 단 **최소 비용**이 조건입니다.
1. 무료 구간(Firebase·GA4·GTM·Looker Studio)을 **먼저 소진**합니다
2. 초과가 실제로 발생하는 도구**만** 유료 전환하고, 전환 전에 「무료 대안으로 대체 가능한가」를 검토합니다
3. 월 사용량·단가·예상 청구액을 대시보드에 노출합니다 — 보이지 않는 비용은 통제되지 않습니다
4. **월 예산 상한은 아직 미정**입니다(§8-2). 상한이 정해지기 전에는 종량 과금 기능(세션 리플레이 등)을 **기본 OFF**로 둡니다

### 3-9-2. 먼저 인정할 것 — 지금 트래픽으로는 A/B가 성립하지 않는 구간이 있습니다

웹 7일 **427클릭 · 전환 0** 수준에서는 결제 같은 저빈도 전환의 A/B 테스트가 **통계적으로 판정되지 않습니다.** 억지로 돌리면 "차이 없음"만 반복해서 나옵니다.

| 지표 성격 | 판정 방법 |
|---|---|
| 고빈도(노출·탭·스크롤·섹션 도달) | **A/B 가능** — Remote Config 배분 |
| 저빈도(결제·상담 신청) | **A/B 불가** → 대체: 전후 비교 + 미노출 세그먼트 대조 + 정성 관찰(사용자 5명) |

> 대체 판정을 쓸 때는 **왜 A/B가 불가능한지와 대체 방법을 실험 등록 화면에 반드시 적습니다.** 빈칸이면 등록되지 않습니다.

### 3-9-3. CRO 자동화 루프

| 단계 | 하는 일 | 레벨 |
|---|---|---|
| ① **탐지** | 퍼널 단계별 이탈률이 기준선 대비 악화 → 알림. **자동으로 실험을 시작하지 않습니다** | **L3** |
| ② **가설·변형 초안** | 에이전트가 변형안 3개 + 성공지표 1 + **가드레일 지표 최소 1** + 최소 표본·기간·롤백 조건을 채워 제출 | **L2** |
| ③ **배분·모니터링** | 승인된 실험을 Remote Config에 등록, 50/50 배분, 매일 상태 갱신 | **L1** |
| ④ **판정** | 최소 표본·기간 도달 후 결과 요약 + 권고. **최종 적용은 사람** | **L2** |
| ⑤ **롤백** | 가드레일 지표(이탈·오류·결제 실패·CS 문의)가 악화되면 **즉시 원복** 후 통지 | **L1** |

**중간 피킹 금지** — 최소 표본·기간에 도달하기 전에는 승패를 표시하지 않습니다. 화면에 「판정 가능까지 n건 / n일」만 보여줍니다. 이걸 막지 않으면 유리한 시점에 멈추게 됩니다.

### 3-9-4. 실험 등록 필수 항목 — 하나라도 비면 반려

가설 / 변형(대조군 포함) / **성공지표 1개** / **가드레일 지표 최소 1개** / 최소 표본 / 최소 기간 / 롤백 조건 / A/B 불가 시 대체 판정 방법.

> **가드레일이 비어 있는 실험은 등록할 수 없습니다.** "발견은 늘었는데 경험은 나빠진" 상태를 성공으로 읽는 것을 막기 위한 장치입니다.

### 3-9-5. 첫 분기에 돌릴 실험 후보 (매출 1순위 기준)

| # | 대상 | 가설 | 판정 |
|---|---|---|---|
| 1 | 무통장 미입금 리마인드 문구·시점 | 리마인드가 결제 완료율을 올린다 | 고빈도 → **A/B** |
| 2 | 홈 수익 카드 3종 위치 | 위치에 따라 상세 도달률이 다르다 | 고빈도 → **A/B** |

## 8. 개발 범위 · 미결

- **플랫폼 결정 필요** — 아임웹 head 삽입으로 커버 가능한 범위 vs 별도 백오피스 신규 구축. (D1 회신 연동)
- **회원 계정 통합** — 웹·시놀앱·시럽앱 user 체계 동일 여부(D2)가 자동 초대·설치 기여의 전제
- **이벤트 예산·어뷰징 정책** — 경영 결정 대기
- **개인정보 경계** — 회원 상세는 이 도구에서 조회하지 않음(집계만). 개인정보 처리 방침·접근 통제 별도 확인
### 8-1. 2026-08-09 경영 확정 3건 — 더 이상 검토 항목이 아닙니다

| # | 확정 | 설계 반영 |
|---|---|---|
| ① | **GitHub + Linear 병행** | GitHub = 코드·이슈·릴리즈의 기록 원본, Linear = 일정·사이클·담당 배치. 에이전트가 **양쪽을 동기화**하며 상태의 원본은 **GitHub 이슈**로 고정합니다(두 곳에서 서로 다른 상태가 되는 것을 막기 위함) |
| ② | **분석 도구 초과분 예산 집행 허용** — 단, 최소 비용 | 무료 구간(Firebase·GA4·GTM·Looker Studio)을 먼저 소진하고, **초과가 발생하는 도구만 유료 전환**합니다. 전환 전 「무료 대안으로 대체 가능한가」를 먼저 검토하고, 월 사용량·단가를 대시보드에 노출합니다 |
| ③ | **QA 창구 통합 진행** | 카톡·구두 접수를 **백오피스 ⑨ QA·개선 요청 단일 창구로 통합**합니다. 슬랙은 **접수처가 아니라 통지처**입니다(에이전트가 결과만 알림). 접수는 백오피스에서만 받습니다 |

> ③의 실패 조건 — 창구를 통합해도 **접수가 어려우면 사람들은 다시 카톡으로 갑니다.** 그래서 접수는 「신고」 버튼 한 번이고 재현 절차를 쓰게 하지 않습니다(3-8). 통합 성공 여부는 **백오피스 접수 비율**로 측정합니다.

### 8-2. 남은 미결

- **플랫폼 결정 필요** — 아임웹 head 삽입으로 커버 가능한 범위 vs 별도 백오피스 신규 구축. **이 초안이 개발 착수 문서가 되려면 먼저 정해져야 합니다** (D1 회신 연동)
- **분석 도구 월 예산 상한** — ②에서 집행은 승인됐으나 **금액 상한은 미정**. 상한 없이 종량 도구를 켜면 사용량이 늘 때 비용이 따라 늡니다
- **이벤트 예산·어뷰징 정책** — 경영 결정 대기 (금액·1인 상한)
- **단체미팅 가격 등급** — 99,000~300,000원 3배 편차의 구독 커버 등급
