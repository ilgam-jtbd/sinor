## 0. 이 문서의 목적

기획이 만든 판단을 디자이너와 개발자가 **다시 해석하지 않고** 바로 쓸 수 있게 만드는 것이 목적입니다.
그러려면 세 가지가 규격화되어 있어야 합니다.

1. **무엇을 왜 만드는가** — 지표 계층에서 내려온 근거 (PO 교육자료 W2)
2. **어떻게 생겼는가** — 목업과 컴포넌트 규격
3. **어떤 순서로 짜는가** — 코딩 에이전트가 바로 실행 가능한 티켓과 프롬프트

이 문서는 그 세 가지의 형식을 고정합니다. 내용이 아니라 **형식**을 정하는 문서입니다.

## 2. 3자 역할 분담

WHO-37·WHO-47에서 검증된 구조를 시놀에 적용합니다.

| 주체 | 담당 | 산출물 | 하지 않는 것 |
|---|---|---|---|
| **Cowork (시놀)** | 전략 판단 · 문서 최종본 · 이해관계자 커뮤니케이션 | 확정 기획서 · IR 반영 · 의사결정 회신 | 코드 작성 |
| **Claude Code** | 기술 조사 · 구현 · QA · 배포 | 코드 · 기술 실사 보고서 · 테스트 | 전략 판단, 우선순위 변경 |
| **전략기획 (본 세션)** | 진단 · 지표 설계 · 기획서·목업 초안 | 분석 문서 · 목업 · 프롬프트 | 최종 승인 |
| **디자이너 (UX/UI)** | 목업 → 실제 화면 · 컴포넌트 정의 | 디자인 파일 · 토큰 · 상태 정의 | 구조 변경(기획 합의 없이) |

**연결 규칙**
- 판단이 바뀌면 → Cowork가 정본 갱신 → Linear 티켓에 기록 → CC가 읽고 반영
- 구현이 불가능하면 → CC가 Linear 티켓에 제약 보고 → Cowork가 대안 결정 → 기획서 갱신
- **어느 쪽도 상대 영역에서 임의 결정하지 않습니다.** 막히면 티켓에 남기고 넘깁니다.

## 3. Linear 사용 규격 — 결정 필요

### 3-1. 워크스페이스 분리 문제

현재 Linear은 `whocareskorea` 단일 팀입니다. 시놀 이슈를 여기 만들면 이슈 키가 `WHO-xx`가 되어 후케어스와 섞입니다. 두 회사의 문서·지표를 섞지 않는다는 기존 원칙과 충돌합니다.

| 선택지 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A (권장)** | Linear에 `Sinor` 팀 신설 → `SIN-xx` 키 | 완전 분리. 지표 오염 없음 | 팀 생성은 사람이 직접 해야 함 |
| B | 같은 팀에 시놀 프로젝트 + `SINOR:` 라벨 | 즉시 시작 가능 | 이슈 키가 WHO-xx로 섞임 |
| C | Linear 미사용, 문서 파일로만 교환 | 설정 불필요 | 상태 추적 불가 |

**권고 — A.** Linear에서 팀을 하나 만들고 알려주시면 아래 구조를 바로 세웁니다. 급하면 B로 시작하되 라벨을 반드시 붙입니다.

### 3-2. 프로젝트 구조 (팀 확정 후 생성)

```
프로젝트: 시놀 앱·웹 전환 개편
요약: 앱 홈·채팅 개편 + 웹 앱설치 전환 동선. 종합전략 v3 S11·S15 실행.
      Cowork(전략·최종문서) ↔ CC(코드) ↔ 전략기획(진단·목업) 3자 싱크.
```

### 3-3. 라벨 체계

후케어스의 `APP:CUST` / `PLATFORM` / `DESIGN` 패턴을 따릅니다.

| 라벨 | 대상 |
|---|---|
| `APP:HOME` | 앱 홈 화면 |
| `APP:CHAT` | 앱 채팅 |
| `WEB` | sinor.co.kr |
| `MEASURE` | GA4·전환추적·이벤트 |
| `DESIGN` | 디자인 산출물 필요 |
| `DECISION` | 의사결정 대기 |
| `EXTERNAL` | 하나투어·PG·스토어 등 외부 의존 |

### 3-4. 티켓 제목 규칙

```
[구분] 제목 — 부연 (판정 조건)
```
예시
- `[MEASURE] GA4 search_term 수집 + 결과 0건 로그 — 홈 검색바 개발 선행`
- `[WEB] 단체미팅 독립 URL /meeting 신설 — 앵커 구조 제거 (색인 확인까지)`
- `[DECISION] Q7 웹 플랫폼 코드 수정 가능 범위 — A군 7개 요구사항의 전제`

### 3-5. 커뮤니케이션 스레드 티켓

WHO-37 방식대로, 세션 간 대화를 담는 티켓을 하나 둡니다.

```
제목: [싱크] Cowork(시놀) ↔ CC ↔ 전략기획 커뮤니케이션 스레드
본문: 세 세션 링크 + 이번 주 결정사항 + 대기 중 질문
운영: 각 세션이 판단을 바꾸거나 막히면 이 티켓에 댓글로 남긴다.
```

## 4. 문서 파이프라인 — 진단에서 코드까지

```
① 진단 (실측)          → 지표 계층 + 병목 식별
② One-pager (PRD)      → 무엇을 왜, 성공지표와 가드레일
③ 목업 (와이어프레임)   → 구조 합의
④ 디자인 (UI)          → 실제 화면 + 컴포넌트 토큰
⑤ 티켓 (Linear)        → 실행 단위로 분해
⑥ 에이전트 프롬프트    → CC / Codex 실행
⑦ 검증 (A/B·지표)      → 성공지표·가드레일 판정
⑧ 이터레이션          → ①로 복귀
```

**각 단계는 이전 단계의 산출물 없이 시작하지 않습니다.** 특히 ②를 건너뛰고 ⑤로 가면, 개발은 되는데 왜 만들었는지 아무도 모르는 상태가 됩니다.

## 5. One-pager 템플릿 (필수 양식)

모든 기능은 개발 착수 전 이 한 장을 통과합니다. PO 교육자료 W3의 Four customer questions를 그대로 씁니다.

```markdown
# [기능명] One-pager

## 푸는 문제
한 문장. 실측 근거 1개 이상 포함.

## Four Customer Questions
1. 즉시적인 고객은 누구인가?
2. Customer Job은 무엇인가? (그 사람이 해내려는 일)
3. 10배 더 잘해야 하는 것은 무엇인가?
4. 성공지표와 가드레일 지표는 무엇인가?

## 지표 계층
상위 지표 = ___ × ___
내가 올리려는 레버 = ___
현재값 ___ → 목표값 ___ (판정 시점 ___)

## 가드레일
악화되면 실패로 판정하는 지표 2~3개.

## MVP 범위
- 반드시 포함 (critical path)
- 이번에 제외 (엣지 케이스·편의 기능)

## 검증 방법
A/B 테스트 설계. 불가능하면 왜 불가능한지와 대체 판정 방법.
```

**가드레일이 비어 있으면 반려합니다.** 성공지표만 있는 기획은 "발견은 늘었는데 경험은 나빠진" 상태를 성공으로 오독합니다.

## 7. 코딩 에이전트 프롬프트 규격

CC와 Codex는 성격이 달라 같은 프롬프트를 쓰면 결과가 나빠집니다.

| 구분 | Claude Code | OpenAI Codex |
|---|---|---|
| 강점 | 저장소 전체 맥락 · 다중 파일 · 명령 실행 · 조사 | 명확히 정의된 단일 작업 · 빠른 구현 |
| 프롬프트 | 목표와 제약 중심. 탐색 여지를 남김 | 입출력·파일 경로·완료 조건을 못 박음 |
| 적합 작업 | 기술 조사 · 구조 변경 · 리팩터링 · QA | 컴포넌트 구현 · 이벤트 부착 · 스타일 |

### 7-1. CC 프롬프트 골격

```markdown
## 역할
[이 저장소에서 무엇을 하는 사람인가]

## 목표
[비즈니스 목표 1줄 — 왜 하는지]

## 근거
[실측 수치 · One-pager 링크]

## 작업
1. [탐색] 현재 구조를 먼저 파악한다: ___
2. [구현] ___
3. [검증] ___

## 제약
- 프로덕션 변경 금지 / 개인정보 접근 금지
- 기존 ___ 동작을 깨지 않는다
- 불가능하면 대안을 제시하고 멈춘다 (임의 우회 금지)

## 완료 조건
- [ ] ___
- [ ] 이벤트 부착: ___
- [ ] 테스트 통과

## 출력
[파일 경로 · 보고서 형식]
```

### 7-2. Codex 프롬프트 골격

```markdown
파일: [정확한 경로]
작업: [한 문장]

입력: [props / 데이터 구조]
출력: [렌더 결과 / 반환값]

요구사항:
- [구체적 항목 1]
- [구체적 항목 2]

제약:
- 기존 [X] 인터페이스 유지
- [Y] 라이브러리만 사용

완료 조건:
- [ ] [검증 가능한 조건]
```

### 7-3. 공통 금지 사항 (두 에이전트 모두)

- 추측을 사실로 쓰지 않는다. 근거를 함께 적는다
- 요구사항을 임의로 확장하지 않는다. 필요하면 티켓에 제안으로 남긴다
- 측정 이벤트를 나중으로 미루지 않는다. 같은 작업에 포함한다
- 막히면 우회하지 말고 보고한다

## 8. 디자인 핸드오프 규격

디자이너가 목업을 받아 작업할 때 **함께 확정해야 하는 것**입니다. 이것이 없으면 개발 단계에서 다시 물어봅니다.

| 항목 | 내용 |
|---|---|
| 상태 정의 | 기본 · 눌림 · 비활성 · 로딩 · 빈 상태 · 오류 |
| 접근성 | 본문 최소 17px · 터치 영역 최소 48px · 명도 대비 4.5:1 |
| 반응형 | 최소 지원 화면폭 · 긴 텍스트 줄바꿈 처리 |
| 이미지 규격 | 모임 카드 · 배너 · 미등록 시 기본 이미지 |
| 컴포넌트 재사용 | 수익 카드는 콘텐츠 카드와 **동일 컴포넌트** (v3 원칙) |
| 다크모드 | 지원 여부 결정 |

**디자인이 구조를 바꾸려면** 목업 단계로 되돌아가 기획과 합의합니다. 디자인 단계에서의 구조 변경은 개발 재작업을 만듭니다.

### 9-2. 전략 미결 1건 — 우선순위 최상

**2026E 16억 처리.** 7개월 실적 2.03억(연환산 3.5억)과 나란히 놓이면 방어가 어렵습니다. IR 덱·TIPS 메모·재무모델 세 문서가 동시에 걸려 있습니다.

선택지 — ① 실적선·계획선 분리 표기 ② 하향 재확정 ③ 시점 이동(Pre-A 클로징 후 12개월)

### 9-3. 표기 주의 1건

종합전략 v3 커버·S2·S5·S14의 **가입 CAC 2,836원은 계획값**입니다(월 예산 5,672,000 ÷ 계획 신규 2,000명). 실제 월 신규는 922~1,361명. 내부용은 무방하나 외부 문서에서는 "계획 기준" 병기 또는 실측치 교체가 필요합니다.

## 10. 첫 스프린트 제안 (2주)

측정이 없으면 이후 모든 판단이 근거를 잃으므로, 측정과 조사를 먼저 놓습니다.

## 11. Cowork에 넘기는 요청 3가지

1. **Linear 팀 분리 여부를 결정해 주십시오** (3-1 선택지 A/B/C). 결정되면 프로젝트·라벨·티켓 구조를 바로 세웁니다.
2. **CC 세션에 기술스택 조사 프롬프트 v2를 전달해 주십시오.** 본 세션에서는 CC 세션에 직접 게시할 수 없습니다.
3. **2026E 16억 처리 방향을 정해 주십시오.** 제품 개발과 별개로, 이 결정이 늦어질수록 IR·TIPS 문서 정리가 계속 미뤄집니다.

## 부록 — 판단 기준 요약 (PO 교육자료 W1~W4)

의사결정이 갈릴 때 돌아올 기준입니다.

- **좋은 문제** = 겪는 사람 수 × 고통의 크기 ÷ 필요한 리소스. 목표는 단위시간당 임팩트 최대화
- **지표는 쪼갠다** — 매출 = 판매건수 × 건당 금액 / 활성유저 = f(신규, 리텐션, 부활)
- **레버 우선순위** — 전환율이 높은데 비중이 낮은 곳을 먼저 키운다
- **최초 가설의 90% 이상은 틀린다** — 그래서 작게, 빠르게, 측정 가능하게
- **A/B 테스트는 필수(must)** — 불가능하면 왜 불가능한지 적는다
- **요구사항을 그대로 만들지 않는다** — 기저의 문제를 이해하고 최소 리소스 해법을 제시한다
- **생애주기별로 운영 방식이 다르다** — P/M Fit 이전은 속도, 이후는 실행 퀄리티

시놀은 세 제품의 생애주기가 다릅니다. 시럽인연은 Maturity(실행 퀄리티·예산 집중), 시놀 커뮤니티는 Growth 종료(비용 개선·자동화), 시니어 일자리는 Introduction(개발 없는 검증). **같은 방식으로 운영하면 안 됩니다.**
