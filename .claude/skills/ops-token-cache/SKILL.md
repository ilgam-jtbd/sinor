# Claude Code 프로젝트 최종 운영 지시

Token / Context / Cache Optimization + Development / QA / Redesign

> 이 문서는 Claude Code가 이 프로젝트에서 작업하는 기본 운영 원칙이다.
> 목표는 단순히 토큰을 적게 사용하는 것이 아니라 동일한 품질을 더 작은 컨텍스트와 높은 캐시 적중률로 달성하는 것이다.

> 이 저장소 적용 메모(CC, 2026-09-03): §19 codebase-overview는 이 저장소에 앱 코드가 없어 해당 없음 — 문서 지도 역할은 `docs/12_자산대장_2026-08.md`와 `/hub/`가 대신한다. §6 환경변수는 실제 인증 방식·버전 확인 전이라 미적용(지시 본문의 원칙대로 임의 추가하지 않음).

## 1. 최우선 원칙

모든 작업에서 다음 우선순위를 따른다.

정확성 > 안전성 > 기존 의사결정 준수 > 작업 범위 준수 > 검증 > 속도 > 토큰 절감

토큰 절감을 이유로 필요한 분석·검증을 생략하지 않는다.

반대로 다음과 같은 불필요한 비용은 적극적으로 제거한다.

- 관련 없는 파일 탐색
- 동일 파일 반복 읽기
- 전체 로그 출력
- 불필요한 MCP 호출
- 불필요한 서브에이전트
- 긴 세션을 무작정 유지
- 모델/effort 반복 변경
- 불필요한 "/compact"
- 방향이 틀렸는데 계속 진행
- 이미 확인한 내용을 다시 확인
- 승인되지 않은 대규모 변경

---

## 2. 모든 요청은 먼저 작업 범위를 확정한다

사용자가 특정 화면·파일·기능을 요청하면 프로젝트 전체를 먼저 스캔하지 않는다.

기본 순서

사용자 요청 확인 → 작업 범위 확정 → 관련 파일 최소 탐색 → 관련 문서/Decision 확인 → 현재 구현 확인 → 실행 → 관련 범위만 검증 → 결과 요약

금지 — 다음과 같은 광범위한 요청으로 시작하지 않는다.

전체 repository scan · 모든 문서 읽기 · 모든 MCP 확인 · 전체 로그 출력 · 전체 테스트 실행

필요성이 확인된 경우에만 범위를 넓힌다.

---

## 3. 작업 유형에 따라 모델과 effort를 결정한다

단순 작업 (문구 수정 · CSS 수정 · 특정 함수 수정 · 작은 버그 수정 · 단순 조회) → Sonnet / low

일반 개발 (기능 추가 · API 수정 · 화면 개선 · 일반 리팩터링) → Sonnet / medium

복잡한 작업 (아키텍처 변경 · DB 구조 변경 · 대규모 리팩터링 · 복합적인 원인 분석 · 여러 시스템에 영향을 주는 설계) → Plan 단계 후 필요한 경우에만 Opus / high 이상

Opus와 높은 effort를 기본값으로 사용하지 않는다.

---

## 4. 모델과 effort는 세션 초반에 결정한다

세션 중 불필요하게 다음을 변경하지 않는다.

- "/model"
- "/effort"
- opusplan 전환
- fast mode의 불필요한 on/off

이유: 모델과 effort 변경은 캐시 프리픽스에 영향을 줄 수 있다.

따라서 작업 시작 시 적절한 설정을 선택하고 가능한 한 유지한다.

---

## 5. Prompt Cache를 적극적으로 보호한다

Claude Code의 비용과 성능에서 다음 두 가지를 핵심 지표로 본다.

① Context size
② Cache hit rate

가능하면 동일한 프리픽스를 유지한다.

세션 중 피해야 할 행동

- 모델 변경
- effort 변경
- 불필요한 MCP 서버 연결/해제
- 불필요한 플러그인 변경
- 작업 중간의 대규모 도구 구성 변경
- 불필요한 compact

원칙: 세션 중 프리픽스를 흔들지 않는다.

---

## 6. Cache TTL을 고려한다

캐시는 계속 적중하면 유지되므로 작업을 지속하는 동안에는 캐시가 살아 있을 수 있다.

따라서 장시간 자리를 비운 뒤 복귀하는 경우에는 첫 요청의 비용 증가 가능성을 고려한다.

API / Bedrock 등의 환경에서는 프로젝트 정책과 실제 환경을 확인한 뒤 필요하면 `ENABLE_PROMPT_CACHING_1H=1` 사용을 검토한다.

단, 환경변수는 실제 인증 방식과 현재 Claude Code 버전을 확인한 후 적용한다. 문서에 없는 설정값을 임의로 추가하지 않는다.

---

## 7. 작업 종료/전환에 따른 세션 명령 선택

| 상황 | 우선 명령 |
|---|---|
| 완전히 다른 작업 | `/clear` |
| 같은 작업이지만 컨텍스트가 커짐 | `/compact` |
| 잘못된 방향으로 진행 | `/rewind` |
| 세션을 나중에 다시 찾을 필요 | `/rename` 후 `/clear` |
| 이전 세션 재개 | `/resume` |

`/clear` — 무관한 작업으로 넘어갈 때. 예: AEO 분석 → /clear → 결제 기능 개발. 이전 작업의 불필요한 대화를 새 작업으로 가져오지 않는다.

`/compact` — 같은 작업을 계속하지만 컨텍스트가 지나치게 커졌을 때. 작업이 의미 있는 단계에 도달한 후 실행한다. 예: 분석 완료 → compact → 구현 → 테스트.

Compact 시 반드시 보존: 사용자 요구사항 · 확정된 의사결정 · 변경된 파일 · 핵심 구현 내용 · 테스트 결과 · 미해결 이슈 · 다음 작업. 탐색 과정의 중복 내용과 장황한 로그는 제거한다.

`/rewind` — 방향이 잘못된 경우 compact하지 말고 rewind를 우선 검토한다. 잘못된 방향을 요약해서 계속 가져가는 것은 금지한다.

---

## 8. 대규모 세션은 오래 유지하지 않는다

하나의 세션에서 전체 분석 → 리디자인 → 개발 → QA → SEO → AEO → 다른 기능 → 문서 작성을 모두 이어서 하지 않는다.

작업 단위를 의미 있게 분리한다. 예: Session A AEO/GEO 진단 · Session B UX/UI 리디자인 · Session C 구현 · Session D QA · Session E 최종 SEO/AEO 재측정.

각 세션에는 필요한 컨텍스트만 유지한다.

---

## 9. Claude Code 업그레이드 이후 큰 세션 resume 주의

업그레이드 후 오래된 대형 세션을 바로 resume하면 캐시 효율이 크게 떨어질 수 있다.

업그레이드 전: 작업 단계 종료 → 핵심 결정/변경사항 정리 → compact 또는 새 세션 준비.

업그레이드 이후에는 필요 이상으로 오래된 대형 세션을 그대로 이어가지 않는다.

---

## 10. `/context`로 컨텍스트를 진단한다

컨텍스트가 무거워졌다고 느껴지면 `/context`로 System prompt · System tools · MCP tools · Memory / CLAUDE.md · Messages · Free space를 확인한다. MCP tools 또는 Messages가 과도하게 크면 원인을 찾는다.

---

## 11. `/usage`로 비용을 확인한다

중요 작업 전후 또는 비용 증가가 의심되는 경우 `/usage`로 Input · Output · Cache read · Cache creation · Uncached · MCP attribution · Long context · Cache misses를 확인한다.

해석: Cache read ↑ / Cache creation ↓ → 양호. Cache creation이 반복적으로 높음 → 프리픽스가 계속 변경되는지 확인. Messages가 과도하게 큼 → 세션 분리 또는 compact 검토. MCP tools가 과도하게 큼 → MCP 구성 검토.

비용 최적화는 추측으로 하지 말고 가능한 경우 측정값으로 판단한다.

---

## 12. MCP는 필요한 것만 사용한다

MCP 도구 정의 자체가 컨텍스트를 차지할 수 있다. 작업에 필요하지 않은 MCP는 사용하지 않는다.

가능한 경우 CLI를 우선한다. 예: git → git · GitHub → gh · AWS → aws · 테스트 → package scripts / CLI. MCP가 더 적합한 경우에만 MCP를 사용한다.

---

## 13. MCP 서버 구성 변경은 작업 중 최소화한다

MCP 서버 추가/제거 · 플러그인 변경 · tool 구성 변경은 캐시에 영향을 줄 수 있으므로 작업 중 불필요하게 수행하지 않는다. 특히 대규모 작업 중간에 도구 구성을 바꾸지 않는다. 필요하면 작업 단위를 종료한 후 변경한다.

---

## 14. 큰 로그는 절대로 그대로 컨텍스트에 넣지 않는다

수천 줄 테스트 로그 · 서버 로그 · build 로그 · 대형 JSON · generated 파일 · lock 파일 · node_modules · 대량 API response를 전체 출력하지 않는다.

먼저 필터링한다. 예: `npm test 2>&1 | grep -A 5 -E 'FAIL|ERROR|error:' | head -100`. 프로젝트 환경에 맞는 더 정확한 필터가 있으면 그것을 사용한다.

목표: 수만 토큰의 로그 → 실제 원인 수백 토큰.

---

## 15. 서브에이전트는 장황한 작업 격리에 사용한다

대량 로그 분석 · 긴 테스트 · 문서 분석 · 반복적인 탐색 · 단순 검증은 필요하면 서브에이전트로 격리하고 부모 세션에는 결과만 요약한다.

단, 서브에이전트 자체에도 별도 컨텍스트와 비용이 발생하므로 무조건 사용하지 않는다. 실제로 비용/컨텍스트를 줄이는 경우에만 사용한다.

---

## 16. Agent Team은 최소 사용

병렬 에이전트는 실제 병렬성이 필요하고, 작업이 명확히 분리되고, 각각 독립적인 산출물이 필요한 경우에만 사용한다. 단순 탐색이나 작은 작업에는 사용하지 않는다. 작업 완료한 에이전트는 즉시 종료한다.

---

## 17. CLAUDE.md는 200줄 이하를 원칙으로 한다

CLAUDE.md에는 프로젝트 핵심 구조 · 중요한 코딩 규칙 · 테스트 명령 · 핵심 금지사항 · 중요한 Architecture Decision · 반드시 지켜야 하는 UX/SEO/AEO 원칙만 둔다. 상세 워크플로우는 Skills로 분리한다.

---

## 18. Skills로 작업별 지침을 분리한다

예: `.claude/skills/` 아래 aeo/ geo/ seo/ ux-qa/ redesign/ testing/ codebase-overview/. CLAUDE.md에 수백 줄의 상세 지침을 넣지 않는다. 필요한 작업에서만 Skill을 호출한다.

---

## 19. Codebase Overview를 유지한다

프로젝트 구조를 매번 다시 탐색하지 않도록 `docs/architecture/codebase-overview.md`를 유지한다 — 주요 디렉토리 · 주요 페이지 · 핵심 컴포넌트 · API · DB · 인증 · 테스트 · 배포 · 핵심 의존관계. 단, 실제 코드와 다른 내용은 기록하지 않는다.

---

## 20. UX/UI 리디자인 작업은 분석 후 실행

리디자인 요청을 받으면 즉시 디자인하지 않는다.

현재 화면 실측 → 기존 구현 확인 → 관련 문서/Decision 확인 → 기존 QA 확인 → 문제 정의 → 가상 고객 가설 → UX Task / QA 설계 → 리디자인 후보 → Founder 승인 → 구현 → QA → 재측정

Defect와 Redesign Candidate를 반드시 분리한다.

---

## 21. AEO/GEO/SEO 개선도 측정 후 실행

현재 페이지 → metadata → JSON-LD → canonical → sitemap / robots → 내부 링크 → 콘텐츠 구조 → AI crawler → E-E-A-T 순서로 확인한다. 필요하지 않은 전체 사이트 분석은 하지 않는다.

---

## 22. AI 검색 최적화 기준

필요에 따라 확인: 명확한 H1 · 직접 답변 가능한 첫 문단 · 질문형 H2/H3 · 핵심 정보의 구조화 · 목록/표 · FAQ · 대상 사용자 · 서비스 가치 · 이용 방법 · 최신성 · 작성자/검토자/운영주체 · Organization · WebSite · WebPage · Service · WebApplication · BreadcrumbList · FAQPage · Person / Article.

실제 존재하지 않는 정보는 생성하지 않는다. 특히 가짜 전문가 · 가짜 작성자 · 가짜 회사 정보 · 가짜 SNS · 가짜 sameAs · 가짜 통계 · 가짜 고객 · 가짜 리뷰를 만들지 않는다.

---

## 23. Evidence 표기

분석 결과는 `[실측]` `[가상]` `[가상·오해]` `[추정]` `[문서에 없음]` 구분을 유지한다.

가상 고객 테스트는 실제 사용자 테스트로 표현하지 않는다. 문서에 없는 내용은 임의로 보완하지 않고 "문서에 없음"이라고 기록한다.

---

## 24. 개발 후 검증

변경 파일 확인 → lint → typecheck → 관련 unit test → 관련 integration/e2e → browser QA

전체 테스트가 필요하지 않은 작은 수정에는 전체 테스트를 강제하지 않는다.

---

## 25. Browser QA

화면 관련 변경은 가능하면 실제 브라우저에서 확인한다. 우선순위: Android Chrome → Android Naver in-app → iOS Safari → iOS Kakao in-app → Desktop Chrome. 프로젝트의 기존 QA 기준이 있으면 그 기준을 우선한다.

---

## 26. 수정과 리디자인을 혼동하지 않는다

Defect — 현재 구현이 요구사항/결정사항과 다른 문제. 기록: 증상 · 재현 · 기대값 · 실제값 · 근거 · 심각도.

Redesign Candidate — 현재 구현은 정상이나 UX/UI/전환/AEO/GEO 등의 관점에서 개선할 가능성이 있는 제안. 기록: 현재 상태 · 문제 · 근거 · 제안 · 기대효과 · Founder Decision.

각각 별도로 기록한다.

---

## 27. Founder 승인 없는 대규모 변경 금지

URL · DB schema · 사업 로직 · 가격 · 핵심 CTA · 승인된 Copy · robots · noindex · SEO 전략 · 대규모 디자인 · 외부 서비스 설정 · 배포 전략은 별도 승인 없이 임의 변경하지 않는다.

범위를 넘어서는 경우 다음과 같이 보고한다.

```
[승인 필요]
현재 요청 범위를 넘어서는 변경입니다.
```

---

## 28. 자동화는 비용 효과가 있을 때만 도입

Hook, Skill, Script, Subagent 등을 무조건 추가하지 않는다. 반복 작업이 많음 + 컨텍스트 절감 효과가 있음 + 유지보수 비용이 낮음 = 자동화 후보. 특히 긴 로그를 전처리하는 Hook은 적극 검토한다.

---

## 29. 유휴 세션도 관리한다

필요하지 않은 세션을 장시간 열어두지 않는다. scheduled task, cross-session message, goal check-in 등으로 불필요한 요청이 발생할 수 있으므로 사용하지 않는 자동 동작은 점검한다. 비용이 발생하는 자동 작업을 임의로 추가하지 않는다.

---

## 30. 작업 전환 시 가장 중요한 규칙

먼저 판단한다: "이 작업은 방금 하던 작업과 같은 작업인가?"

YES → 컨텍스트 유지. 필요하면 `/compact`.
NO → `/clear`.
방향이 잘못됨 → `/rewind`.

이 세 가지를 혼동하지 않는다.

## 31. 최종 실행 프로토콜

① 요청 범위 확인 ② 작업 유형 판단 ③ 모델 / effort 결정 ④ 관련 파일 최소 탐색 ⑤ 기존 Decision / 문서 확인 ⑥ 현재 구현 확인 ⑦ 최소 실행 계획 ⑧ 필요한 파일만 수정 ⑨ 관련 테스트 ⑩ Browser QA 필요 여부 판단 ⑪ /usage /context 필요 여부 판단 ⑫ 결과 요약 ⑬ 같은 작업이면 계속 ⑭ 컨텍스트가 커지면 /compact ⑮ 다른 작업이면 /clear ⑯ 방향이 틀리면 /rewind

```
- typecheck:
- test:
- browser QA:

- 필요한 경우 1개
```

전체 로그와 전체 diff를 답변에 복사하지 않는다.

## 33. 최종 목표

작게 탐색하고, 작게 수정하고, 필요한 것만 검증하고, 긴 컨텍스트를 만들지 않고, 캐시를 가능한 한 유지하고, 불필요한 MCP와 에이전트를 줄이고, 작업이 끝나면 세션을 정리한다.

> "더 적은 토큰으로 더 많은 일을 하는 것"이 아니라
> "불필요한 토큰을 쓰지 않으면서 필요한 품질은 그대로 유지하는 것"

모든 비용 최적화는 품질 저하가 없어야 하며, 중요한 분석·검증을 생략하는 방식의 절약은 허용하지 않는다.
